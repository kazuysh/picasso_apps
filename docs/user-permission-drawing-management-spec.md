# ユーザー権限と図面管理仕様

## 目的

ログイン中ユーザーの権限に応じて、図面の保管可否、ステータス変更可否、保管時の所有者を制御する。

一般ユーザーは自分の作成した図面で、ステータスが「設計中」の文書のみ保管できる。特権ユーザーはステータスに制限されず、ステータス変更も可能とする。

## ユーザー権限

ユーザー情報は `/api/GetSessionUser` から取得する。

```ts
type SessionUser = {
  user_name: string;
  id_admin: number;
  full_name: string;
  update: string;
};
```

| id_admin | 区分 | 権限 |
| --- | --- | --- |
| 0 | 一般ユーザー | 自分名義かつ「設計中」の図面を保管できる。「設計中」から「確認中」への変更はできる。 |
| 1 | 特権ユーザー | どのステータスでも保管できる。保管時にステータス変更できる。 |

ユーザー情報が取得できない場合はセッションをクリアし、ログイン画面へ遷移する。

## 図面UID

図面のUIDは以下の形式とする。

```text
{user_name}_{drawingNo}
```

例:

```text
yamada_A-001
```

図面番号は `input.basic.drawingNoTemp` を保管対象の図面番号として扱う。

## 図面一覧

案件一覧画面では `/api/sessioncheck` からログインユーザーIDを取得し、`storeddata.UID` が `{userID}_` で始まる図面のみ取得する。

```ts
UID: { $regex: `^${userID}_` }
```

一覧で表示するステータスは `storeddata.status` を使用し、未設定の場合は「設計中」とする。

ステータスの選択肢は以下とする。

- すべて
- 設計中
- 確認中
- 承認待ち
- 完了

## 新規作成・コピー作成

新規作成またはコピー作成では、入力された図面番号を `input.basic.drawingNoTemp` に設定し、編集画面へ遷移する。

コピー作成の場合は、選択した案件の作業データを現在の作業状態へ読み込んだ上で、図面番号を指定する。

この時点では正式保管ではなく、作業中データとして扱う。

## 保管処理

保管ボタン押下時に保管確認ダイアログを表示する。

ダイアログ表示時と保管実行直前に `/api/GetSessionUser` を呼び出し、最新のユーザー権限を確認する。

保管処理は以下の順に実行する。

1. 図面番号の入力チェック
2. コピーして保管の整合性チェック
3. ユーザー権限チェック
4. `/api/saveWork` で `workdata` に保存
5. `/api/postWork2Stored` で `workdata` から `storeddata` へ移動

### 図面番号チェック

図面番号が空の場合は保管不可とする。

コピーして保管する場合、元の図面番号と同じ図面番号では保管不可とする。

コピーして保管しない場合、元の図面番号と異なる図面番号では保管不可とする。

## 一般ユーザーの制御

一般ユーザーは `id_admin === 0` と判定する。

一般ユーザーの場合、元図面が自分名義かつ「設計中」で、コピーして保管しない場合のみ、保管確認ダイアログで「設計中」または「確認中」を選択できる。

一般ユーザーが「確認中」として保管した図面は、それ以降は一般ユーザーによる上書き保管を不可とする。

一般ユーザーがコピーして保管する場合は、新しい自分名義の図面として扱い、ステータスは「設計中」とする。

元図面が「設計中」以外の場合、一般ユーザーは上書き保管できない。保管する場合は、図面番号を変えてコピーして保管する必要がある。

保管実行直前にも、一般ユーザーについて以下を確認する。

- コピーせずに上書きする場合、元図面のUIDの `_` より前が現在ユーザーの `user_name` と一致すること
- コピーせずに上書きする場合、元図面のステータスが「設計中」であること
- コピーせずに上書きする場合、選択ステータスが「設計中」または「確認中」であること

元図面が「設計中」以外で上書き保管しようとした場合は、以下のメッセージを表示する。

```text
一般ユーザーはステータスが設計中の図面のみ上書き保管できます。図面番号を変えてコピーして保管してください。
```

保管時に `/api/postWork2Stored` へ渡す `user` は `/api/GetSessionUser` の `user_name` とする。これにより、読み込んだ図面のUIDの `_` より前の部分が現在ユーザーと一致しない場合でも、保管時は現在ユーザー名義のUIDで保存される。

```ts
{
  user: sessionUser.user_name,
  dno,
  overwrite: !copyToStore,
  status: copyToStore ? "設計中" : status,
  full_name: sessionUser.full_name
}
```

## 特権ユーザーの制御

特権ユーザーは `id_admin === 1` と判定する。

特権ユーザーの場合、ステータス選択欄を変更可能とする。

選択可能なステータスは以下とする。

- 設計中
- 確認中
- 承認待ち
- 完了

特権ユーザーは選択したステータスのまま保管できる。

```ts
{
  user: sessionUser.user_name,
  dno,
  overwrite: !copyToStore,
  status,
  full_name: sessionUser.full_name
}
```

## バックエンド連携

### `/api/saveWork`

`saveWork` はログイン中ユーザーと図面番号から `workdata.UID` を作成する。

```text
UID = current_user + "_" + input.basic.drawingNoTemp
```

同じUIDの `workdata` が存在する場合は削除し、新しい作業データを登録する。

### `/api/postWork2Stored`

`postWork2Stored` はリクエストの `user` と `dno` から対象UIDを作成する。

```text
UID = req.user + "_" + req.dno
```

対象UIDの `workdata` を取得し、`storeddata` へ保存する。保存時に以下を設定する。

- `created`: 既存 `storeddata` の作成日時、または現在日時
- `updated`: 現在日時
- `full_name`: リクエストの `full_name`
- `status`: リクエストの `status`。未指定の場合は既存値または「設計中」

`overwrite` が `true` の場合は既存 `storeddata` を上書きする。`false` の場合は同じUIDが存在するとエラーとする。

## 現在の実装上の注意

権限制御は主にフロントエンドで実装されている。バックエンド側の `postWork2Stored` は `id_admin` による保管可否やステータス変更可否を直接検証していない。

そのため、APIを直接呼び出された場合も同じ制限を保証するには、バックエンド側にも以下の検証を追加する必要がある。

- `current_user` と `req.user` の一致確認
- `id_admin === 0` の場合は `status === "設計中"` のみ許可
- `id_admin === 0` の場合は他ユーザーUIDの更新を拒否または現在ユーザー名義へ補正
- `id_admin === 1` の場合のみ任意ステータスを許可

また、`postWork2Stored` にはトランザクション処理で未定義の `client` を参照している箇所があり、現状は例外後のフォールバック処理で保存と削除が行われる。
